# Delivery plan for the provider-neutral platform

Planning edition **0.7.0** · 29 September 2026. Architecture and delivery proposals are unimplemented; upstream facts retain their own verification dates. No compute is provisioned or purchased by this plan.

This sequence implements customer-supplied compute as an architectural boundary from the first core release, then qualifies individual execution and serving profiles. Effort is estimated, funding is unapproved, and all G0–G5 evidence remains future application work.

## First useful release and portability milestone

The visible M1 journey is defined in [gui_workflow.md](gui_workflow.md), with automatic onboarding discovery and admission freshness in [hardware_discovery_and_planning.md](hardware_discovery_and_planning.md). Start setup without an LLM, then use a qualified local assistant. Stage completion follows task-specific evidence; analysis reproduction/review and predictive evaluation remain distinct. The requested output determines the packaging/operation gate.

The first usable release is a GUI-native desktop data workspace with a local harness and filesystem output with governed preparation/EDA, actual tabular classification/regression and a complete service-release path implemented through **WorkloadSpec → ExecutionRequest → ComputeBinding**. The initial binding runs locally with no paid provider dependency; it is the first implementation of the provider-neutral contract. Accept open-ended project collections through D20-bounded ingestion batches of CSV/Parquet, text, PDF and PNG/JPEG under qualified native/OCR profiles. Profile the sources, propose/review a typed relationship graph, validate exact/aggregated/as-of joins and D22 materialisation bounds, then produce a traceable gold product and reproduced analysis pack in the selected folder. Also complete deterministic baselines, actual fitting, bounded optimisation, independent predictive evaluation, notebook/HTML evidence, full pipeline/`predict.py`, HTTP/MCP and clean recipient installation before calling the operational path a service release.

The first provider-portability milestone is **M1 + M1C + M1R**: local core, Colab export/recovery, and the same task contract on customer-funded Runpod with resource/cost reconciliation. These are small vertical slices with their own gates, not a mandate to wait for every cloud. M1 can be used independently while a provider is unavailable. The non-training data-analysis path and four ML/AI workload families remain separate staged capabilities; no GPU training claim arises from completing V1.

Include a **required local plain-language conversation and development agent**, with inspectable typed intent/code, genuine progress, pause/cancel/resume/change controls and durable reconnect. The agent generates and runs bounded Python/SQL in a restricted VM and produces real notebook/report artifacts; no optional-chat shortcut satisfies M1. Qualify the local assistant model separately from the fitted task models. CLI/SDK, source/licence, typed errors, diagnostics, export and restore remain included. Synthetic fixtures, runtime/model notices and guest image must be reviewed during implementation. No model, hardware, provider account or nonzero spend grant is assumed available.

## Evidence gates

PASS means all mandatory evidence is present and meets the frozen rule. FAIL means a known criterion is violated. INSUFFICIENT_EVIDENCE means it cannot yet be established, including missing rights/labels/compatibility or material uncertainty. No gate changes its standard to rescue a candidate.

Missing material authority = inconclusive, conflicting rights/use = fail. | Data preparation and bounded development in approved scope; not paid execution without FIN grant |
| G1 Training and evaluation integrity — EO | Assistant interpretation/tool/code-task evaluation and bounded-repair evidence; preparation/source-coverage and independently reproduced analysis evidence; actually fitted baseline/candidates for predictive tasks; code/env/data lineage; train-only fitting; final access denial; frozen oracle; honest report/uncertainty; checkpoint/reproducibility evidence appropriate to adapter | PASS only with required task criteria and integrity controls. Known leakage/changed oracle = fail; underpowered/unrepresentative evaluation = inconclusive for affected claim. | Candidate eligible for release approval; synthetic pass only supports demo claims |
| G2 Packaging, interface and provenance — PUB with Application/SEC | Assistant model/runtime/notice inventory and development provenance separate from inference dependencies; output-kind complete analysis bundle or inference bundle; notebook, HTML/JSON report, reproduction guide; Python inference entry point and HTTP/MCP parity for services; coordinator job parity for both, dependency locks/SBOM/rights, hashes/signature and approvals | PASS when exact candidate behaviour and all required artifacts are preserved. Missing/broken component/permission mismatch = fail; unverified dependency rights/profile = inconclusive. | Distribute privately for qualified installation testing |
| G3 Deployment, isolation, budgets and recovery — PL with SEC/FIN/SO | D16/D19 assistant-independent discovery, capacity/race checks and local assistant/VM qualification; truthful stage/report projections and controls/replay/revisions A24–A38; parser/SQL containment and manual/scheduled monitor semantics as applicable; clean recipient reproduction/install; profile preflight; tenant/access tests; reservation races; cancellation/worker crash/ACK loss; control-plane outage; restore/rollback and load evidence | PASS for each declared profile/delivery model only. ## Acceptance scenarios

These are future tests, not tests run in this session. Record fixture/version, environment, expected/actual result, logs and evidence digest. Broaden only for concrete risk or gate requirements.

| Scenario | Procedure / expected evidence |
|---|---|
| A01 Sealed-set separation | Optimiser credentials try final object download, preview, tracker link, split expansion and error/log access: all denied; evaluator can run authorised evaluation without revealing labels to candidate code. |
| A02 Preprocessing leakage | Place sentinel token/feature only in final partition; fitted vocabulary/statistics exclude it; fold fit lineage is correct. |
| A03 Crash and lost acknowledgement | Kill worker before and after commit; retry same result key; exactly one committed logical result, multiple attempts/costs visible, no unbounded re-run. |
| A04 Stale worker/fencing | Expire lease, admit permitted replacement, let old worker return: old commit rejected; no corrupted release pointer; orphan cost reconciled. |
| A05 Consequential retry ambiguity | Simulator commits action then drops response; retry resolves same action ID and final state contains one effect. For unsupported real provider idempotency, mark inconclusive and stop automatic retry. |
| A06 Tenant isolation | Tenant A requests B's run/artifact, forged object ID, signed URL, retrieval index and cached route: deny without content/existence leakage. Include direct tracker/store path. |
| A07 Cancellation | Cancel queued/running/checkpointed jobs; record acknowledge and stop timestamps, checkpoint validity and incurred cost. Simulate provider that continues charging; no false guarantee of cancellation. |
| A08 Budget exhaustion/race | Two workers concurrently request last reservation; total granted envelope never exceeds approved cap. No new paid call after exhaustion; late receipts remain unsettled until reconciled. |
| A09 HTTP/MCP parity | Same principal/input/release yields equivalent result, review flags, authorisation denial, limits and error semantics on local/remote declared protocol profiles. |
| A10 Control-plane outage | Disconnect hosted coordination for 24 hours while an installed customer service answers authorised local calls; update/telemetry unavailable is visible; no silent model fallback. Local identity/provider dependencies tested separately. |

## Independent recipient portability gate

Give a recipient organisation the release bytes, rights/compatibility/evaluation dossier and documentation, without the author's development environment or credentials. The recipient verifies signatures/hashes, installs the declared profile, binds its identity/storage/permitted dependencies, runs preflight, reproduces the relevant permitted evaluation, calls the Python entry point and an application HTTP client, calls a separately tested MCP client, and performs restore/rollback. No author assistance during the exercise; observe and record where documentation failed.

For customer-data acceptance, the recipient supplies an authorised snapshot and independent labels/contract. A confidential original evaluation set may be accessible only through an approved evaluator; if neither that nor a valid replacement set is available, the behavioural-reproduction claim is inconclusive. Successful installation alone does not pass G4.

## Rollout, updates and change authority

Analysis pilots begin with reviewed findings and manual checks; predictive/service pilots begin in shadow mode with all outputs reviewed. Establish manual baseline and reject/abstain workflow. After G4, use a bounded canary (proposed 5% of eligible cases) and compare quality/error/cost/latency to frozen thresholds; increase only after sufficient labelled outcomes. Five percent is a deployment-risk proposal, not a statistical sample-size justification. Maintain rapid code/model rollback and manual handling path.

Provider revision, fallback model, corpus, significant library, prompt or policy changes trigger a ChangeProposal and regression evaluation. CI checks contracts/rights/signatures; an EO-controlled gate assesses behavioural evidence. Neither a dependency auto-update nor an optimiser may silently change production. Deprecation gives an explicit migration window; withdrawal follows security/rights urgency and recipient notification.
