## Research conclusions and design implications

* Customer-supplied compute is the architecture direction. Colab, ZeroGPU, batch jobs and persistent serving have different execution semantics; one provider name cannot stand for all of them.
* Runpod is the first proposed automated adapter because it tests a bounded customer-resource lifecycle. This is a design judgement, not evidence of lowest price or best performance. HF Jobs is next or a pilot-led substitute; AWS/Azure/CoreWeave follow partner requirements.
* GPU access and current quota terms do not establish data-processing approval, controllable spend, tenant isolation or independent evaluation. Each profile has a G3 evidence gate.
* Current MCP is revision 2026-07-28, with materially different core negotiation from 2025-11-25; design explicit compatibility profiles. The selected Python SDK's Tasks gap makes application job tools the practical initial choice.
* MLflow already covers substantial ML/GenAI tracking, evaluation and packaging. Product differentiation must come from acceptance/handoff controls and task-oriented data/analysis usefulness, not generic tracking or API/MCP generation.
* The official public MCP Registry excludes private servers; use a private catalogue first and a later public metadata projection.
* Current Commission notices report enacted AI Omnibus changes, so the original 2024 AI Act timeline alone is insufficient. Exact amended legal text still needs qualified verification.
* Anaconda environment tooling, cloud containers and warehouse model-serving environments are different deployment products. Each needs a declared installation path and compatibility evidence.
* Official CPU compute examples support a small curated demo; they do not support unlimited hosted training or a complete infrastructure quote.
